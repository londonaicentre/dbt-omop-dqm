# dbt-omop-dqm

This [dbt](https://github.com/dbt-labs/dbt) package provides a suite of data quality and monitoring tests. Some of these tests are specifically designed for datasets conforming to the [OMOP Common Data Model (CDM)](https://ohdsi.github.io/CommonDataModel/cdm54.html).

It uses dbt as a test runner to identify potential data quality issues.

The results generated by these tests are intended to be parsed and visualized using the companion `dqm-dashboard` Python package, located in the `dqm-dashboard/` subdirectory of this repository.

## Overview & Purpose

The primary goal of this package is to establish a robust data quality monitoring framework for OMOP CDM data within a dbt project. Key features include:

*   **OMOP CDM Focus:** Tests are tailored to common data quality checks relevant to the OMOP standard.
*   **Leveraging dbt Tests for Metric Calculation:** This package utilizes dbt's testing framework not just for simple pass/fail assertions, but primarily as a mechanism to *calculate* data quality metrics (e.g., count of NULLs, percentage conformance). The raw metric value is surfaced through dbt's `run_results.json` artifact. By default, these tests will report a 'warn' status in dbt's output, as their main purpose is metric collection, not strict pass/fail evaluation *within* dbt itself.
*   **Decoupled Threshold Evaluation:** Data quality thresholds (e.g., "no more than 5 NULL values", "at least 95% conformance") are defined by the user, via the `meta` block within the test configuration in `.yml` files. The actual evaluation of the calculated metrics against these user-defined thresholds happens *outside* of dbt, within the companion `dqm-dashboard` Python package. This decouples metric calculation (in dbt) from threshold definition and evaluation (in the dashboard). The `dqm-dashboard` reads the metric from `run_results.json` and the threshold configuration from `manifest.json` to determine the final pass/fail status displayed in the dashboard.

## Installation Instructions

### dbt Package Installation

1.  **packages.yml:** Add the following to your `packages.yml` file:

    ```yaml
    packages:
      - git: "https://github.com/londonaicentre/dbt-omop-dqm.git"
        revision: main
    ```
2.  Run `dbt deps` to install the package.

### Python Dashboard Installation

**Using the dbt tests effectively requires the companion `dqm-dashboard` Python package (located in the `dqm-dashboard/` subdirectory) for parsing results and visualization.**

To install the Python package:

1.  Navigate to the `dqm-dashboard` subdirectory within this repository:
    ```bash
    cd dqm-dashboard
    ```
2.  Install the package using `pip` or `uv`. It's recommended to use a virtual environment and install in editable mode (`-e`) if developing:
    
    ```bash
    # Using uv (preferred)
    uv venv
    source .venv/bin/activate # Or .\venv\Scripts\activate on Windows
    uv pip install -e .

    # Using pip
    python -m venv .venv
    source .venv/bin/activate # Or .\venv\Scripts\activate on Windows
    pip install -e .
    ```

3.  Refer to the `dqm-dashboard/README.md` for further details on its usage and configuration.

## Data Quality Tests & Configuration

This package includes several types of data quality tests implemented as dbt macros. Tests are configured in your `.yml` files, and use the `meta` block to specify thresholds for the companion dashboard.

### Generic Tests

These tests are analogous to dbt's built-in generic tests and are applied to specific columns.
All these tests support a threshold and thresold_type parameter. The threshold_type parameter can be static_number or static_percentage (compares against the percentage of violations). 
If these aren't specified then they default to 0 and static_percentage respectively.

#### dqm_completeness_null_count

Checks for NULL values in a column and returns the count/percentage of NULLs.

**Usage:**

```yaml
models:
  - name: person
    columns:
      - name: year_of_birth
        tests:
          - dbt_omop_dqm.dqm_completeness_null_count:
                threshold: 2000
                threshold_type: 'static_number'  
                # Fails the test in the streamlit dashboard if there are more than 2000 nulls in the year_of_birth column.
```

#### dqm_conformance_standard_concept

Verifies if concept IDs in a column belong to the OMOP Standard Vocabulary ('Standard' concepts). Returns the count or percentage of non-standard concepts found.

**Usage:**

```yaml
models:
  - name: condition_occurrence
    columns:
      - name: condition_concept_id
        tests:
          - dbt_omop_dqm.dqm_conformance_standard_concept:
                threshold: 25
                threshold_type: 'static_percentage'
                # Fails the test in the streamlit dashboard if there are more than 25% non standard concepts
```

#### dqm_plausibility_date_order

Checks if end dates in a column occur before start dates in another column for the same model. Returns the count/percentage of violating records.

**Args:**
*   `start_date_column` (required): The column containing the date that should be earlier.
*   `end_date_column` (required): The column containing the date that should be later.

**Usage:**

```yaml
models:
  - name: visit_occurrence
        tests:
          - dbt_omop_dqm.dqm_plausibility_date_order:
              start_date_column: visit_start_date
              end_date_column : visit_end_date
```

#### dqm_plausibility_high_value

Identifies values in a numeric column exceeding a defined upper limit. Returns the count/percentage of violating records.

**Args:**
*   `max_value` (required): The maximum acceptable value.

**Usage:**

```yaml
models:
  - name: measurement
    columns:
      - name: value_as_number
        tests:
          - dbt_omop_dqm.dqm_plausibility_high_value:
              max_value: 1000
              threshold: 10
```

#### dqm_plausibility_low_value

Identifies values in a numeric column below a defined lower limit. Returns the count of violating records.

**Args:**
*   `min_value` (required): The minimum acceptable value.

**Usage:**

```yaml
models:
  - name: measurement
    columns:
      - name: value_as_number
        tests:
          - dbt_omop_dqm.dqm_plausibility_low_value:
              min_value: 0 
```

### Anomaly Tests

These tests look for unexpected deviations or patterns in the data, often requiring comparison against historical data or expected distributions (handled by the dashboard).
_More tests will be added soon._

#### dqm_row_count_anomalies

Monitors significant changes in table row counts over time. This test itself just returns the current row count; the anomaly detection logic resides in the `dqm-dashboard` which compares current counts to historical ones. This test is always applied at model level.

**Usage:**

```yaml
models:
  - name: condition_occurrence
    tests:
      - dbt_omop_dqm.dqm_row_count_anomalies:
          threshold: 15
```

### Singular Tests (Implemented as Generic Macros)

These tests perform more complex, OMOP-specific checks, often involving multiple tables or concepts. They are implemented as generic tests for easier application but do not accept any parameters apart from threshold.
At the moment these only support percentage thresholds but static_number functionality will be added soon.
Since these are effectively singular tests, they will run regardless of where you attach them however it's best to attach them to the recommendations provided.

#### dqm_plausibility_adult_paediatric_diagnoses

Checks for diagnoses inappropriate for a patient's age group (e.g., paediatric diagnoses in adults). Returns the percentage of violating records.
Recommendation is to attach to condition_occurrence as that is the table it primarily uses. 

**Usage:**

```yaml
models:
  - name: condition_occurrence # Applied at the table level
    tests:
      - dbt_omop_dqm.dqm_plausibility_adult_paediatric_diagnoses:
          threshold: 10 
```

#### dqm_plausibility_events_after_death

Identifies clinical events recorded after a patient's recorded death date. Returns the percentage of violating records.
Recommendation is to attach to death model as that is the anchor table.

**Usage:**

```yaml
models:
  - name: death # Applied at the table level
    tests:
      - dbt_omop_dqm.dqm_plausibility_events_after_death:
          threshold: 10
```

#### dqm_plausibility_gender_specific_diagnoses

Checks for diagnoses inconsistent with a patient's recorded gender (e.g., prostate conditions in females). Returns the percentage of violating records.
Recommendation is to attach to condition_occurrence as that is the table it primarily uses.

**Usage:**

```yaml
models:
  - name: condition_occurrence # Applied at the table level
    tests:
      - dbt_omop_dqm.dqm_plausibility_gender_specific_diagnoses:
            threshold: 10
```

## Dashboard Integration

This dbt package focuses solely on executing the data quality tests within dbt to calculate metrics. To visualize results, evaluate thresholds, and track trends, you **must** use the companion `dqm-dashboard` Python package located in the `dqm-dashboard/` subdirectory.

The typical workflow is:

1.  **Run dbt:** Execute `dbt build` or `dbt test`. This generates `run_results.json` and `manifest.json` that contain our thresholds,violations,etc.
2.  **Parse Artifacts:** Run `parse_dbt_artifacts.py`) to process `manifest.json` and `run_results.json` into a table in postgres.
3.  **Transform Results:** Run `transform_run_results.py` to apply the configured thresholds and prepare the data for the dashboard.
4.  **Visualize:** Launch the Streamlit application (`app.py`) from `dqm-dashboard` to view the data quality results.
